# New Article｜从一个主题到简单文章

## 目标

帮助使用者把已经选定的主题说清楚，而不是替使用者制造一个看起来完整的观点。

```text
选定一个主题
→ 确认草稿归属的输出练习；未指定时使用默认练习
→ 自由补充此刻想到的经历和输入
→ 跨时间检索相关记录，整理主题素材地图
→ 使用者补充或校正
→ 必要时进入 Grill Me，只追问空白与矛盾
→ 确认最想表达的一条主线
→ 创建或更新 practices/<输出练习名>/drafts/YYYYMMDD-文章主题.md
→ 基于同一草稿继续打磨
```

## 边界

- 还不知道写什么、尚未选定主题：先请使用者提供或确认一个主题，不替使用者自动选题；
- 只是保存一条新经历或外部输入：分别使用 `capture-journal` 或 `capture-input`；
- 不因为 Review 出现候选方向就自动写文章，必须由使用者选择主题并确认继续；
- 不要求每篇文章都公开，不把社交媒体的流行写法当作默认标准；
- 单篇文章主题不是 Practice 名称；草稿必须归入一个描述持续行动的输出练习；
- 使用者明确只要一次性文章且不希望保存时，可以只在对话中返回；其他情况下按默认输出练习保存；
- 默认保存草稿，但不自动发布。

## 开始前读取

- 根目录 `PROFILE.md`、`.agents/SOUL.md` 与 `practices/README.md`；
- 使用者选定的主题、Review、Daily 路径或直接提供的材料；
- 输出练习已有的 `mission.md`、`current.md` 与 `drafts/` 中同主题草稿；
- 与主题直接相关的 `reviews/`，以及跨时间检索后命中的少量 `daily/journal/`、`daily/inputs/` 或 Practice；
- 使用者已经说明的平台、受众、语气、长度和隐私要求。

不要为了让文章显得丰富而扫描全部私人记录。

## 先确认输出练习

保存草稿前先确定它属于哪个输出练习。不要把本篇文章主题直接当作 Practice 名称。

使用者没有提供输出练习名时，默认使用：

- **目录名**：`weekly-writing`
- **显示名称**：每周写作

这个默认名称表示持续练习把选定主题发展成文章，不代表每一篇都必须公开，也不要求机械地每七天完成一篇。使用者之后可以明确改用其他输出练习。

- 使用者已经指定输出练习或草稿路径：读取该 Practice 的 `mission.md`、`current.md` 和相关草稿；
- 使用者没有指定：直接查找并复用 `practices/weekly-writing/`，不要再询问练习名称；
- `weekly-writing` 尚未立项：直接按下面的最小结构建立 `mission.md` 和 `current.md`，不依赖另一个 Skill，也不要求使用者先提供更多配置；
- 使用者指定了其他尚未立项的练习：确认必要事实后，使用同一最小结构建立；
- 同名目录存在多个或使用者给出的路径有歧义：先请使用者确认，不创建重复 Practice。

首次立项完成后，后续文章默认复用同一个输出练习，除非使用者明确更换。

### 默认 Practice 的最小结构

首次创建 `weekly-writing` 时，直接使用当前已经选定的文章主题初始化，不另外追问练习名、固定周期、受众或反馈方式。只保留有真实内容的字段：

`mission.md`：

```md
# 每周写作

## 为什么存在
把已经选定的主题发展成可以持续修改的文章，让记录逐渐变成自己的表达。

## 做什么
围绕一个主题召回相关经历和输入，问清主线，形成并继续打磨草稿。

## 不做什么
- 不要求每篇文章都公开；
- 不为了完成频率而编造内容或强行下结论。
```

`current.md`：

```md
# 当前一轮

## 当前主题
{使用者已经选定的文章主题}

## 当前动作
召回相关素材，确认表达主线，完成并继续打磨同一篇草稿。

## 草稿位置
drafts/YYYYMMDD-文章主题.md
```

这是输出练习的最小初始化，不代表使用者已经承诺固定发表频率。使用者后续提供了更具体的使命、节奏或反馈方式时，再更新对应文件。

## 先召回和整理主题素材

主题刚确定、个人材料仍少时，不要立即进入连续追问。先给使用者一个低压力的自由补充入口，例如：

> 先把你此刻想到的相关经历、输入、失败、矛盾或片段一口气说出来，不用整理。你也可以说“直接从记录里找”。

等待使用者补充后再整理；已经提供了丰富材料，或明确要求直接检索、直接 Grill Me、直接起草时，不重复这一步。

### 跨时间检索，而不是全量读取

检索范围覆盖全部已有记录，不限最近七天；实际读取范围由主题相关性决定：

1. 先把相关 `reviews/` 当作索引，寻找已经出现过的连接、变化与来源路径；
2. 再搜索 `daily/journal/`、`daily/inputs/` 和必要的 Practice 中与主题相关的文件名、标题、关键词、近义表达和使用者自己的常用说法；
3. 先完整读取少量高相关候选，材料仍有明显空白时再扩大检索；不要从最早日期开始顺序读取全部历史，也不要为了显得充分下载所有文件；
4. Journal 负责提供亲历事件和生活细节，Inputs 负责提供外部触动和当时回应；不要把外部观点写成使用者的经历或判断。

优先使用真实飞书工具提供的标题、内容搜索或目录列举能力；搜索能力不足时，先利用 Reviews 与文件名缩小候选，不要因此批量下载全部云盘文件。检索结果只是云盘中留下的证据，不等于使用者全部人生；不能因为没有搜到就断言某件事没有发生。

### 返回主题素材地图

起草和 Grill Me 前，先在对话中返回一份简洁的主题素材地图，只保留实际有材料的部分：

- **相关经历**：按必要的时间顺序列出具体事件、动作或场景；
- **相关输入**：接触过什么，以及当时真实记录下来的回应；
- **反复线索与变化**：哪些关注、判断或行动跨时间重复或发生改变；
- **矛盾与反例**：哪些材料彼此拉扯，或不支持当前直觉；
- **仍缺少的部分**：哪些关键点云盘里没有答案。

每条事实附上日期和飞书中的相对路径或文件链接。不要粘贴大段原文，也不要把推测混入事实总结。

返回素材地图后，先邀请使用者补充、删减或纠正，尤其询问是否漏掉了没有写进云盘的相关经历。完成这一轮对齐后，再进入 Grill Me；后续问题只针对素材地图中的空白、矛盾和真正需要选择的表达，不重复询问已经有证据回答的内容。

## Grill Me 模式

Grill Me 是素材地图之后可选的深入追问模式。使用者明确说“Grill me”“先问我”“帮我把想法问清楚”时进入；素材已有但尚无清楚主线时也可以主动建议。已有足够材料或使用者明确要求直接起草时，不强制进入。

这个模式不是攻击、辩论或审讯。保持直接、具体和友好，不替使用者预设答案。每次只问一个问题，并根据上一轮回答决定下一问。优先追问：

- **真实发生**：实际做过、经历过或观察过什么？
- **个人关联**：为什么这件事此刻与使用者有关？真正的在意或代价是什么？
- **核心判断**：最想说清楚的那句话是什么？它与常见说法有什么不同？
- **矛盾与反例**：哪里仍不确定、失败过，或存在不支持当前判断的经验？
- **具体细节**：哪个场景、动作、对话或身体感受能让文章落地？
- **对象与边界**：写给谁，哪些隐私不能进入公开稿？

不要按固定题库机械提问，也不要为了“够深”无限追问。当已经有清楚主线、真实证据和必要张力时，先用简短语言返回“我听到的主线、关键经历、仍保留的矛盾和预期读者”，请使用者确认是否按这条线起草。

## 起草门槛

起草前至少需要理解：

1. 使用者围绕这个主题实际做过、经历过或观察过什么；
2. 这个主题为什么在此刻与使用者有关；
3. 至少一个能够进入文章的具体场景、动作、对话或细节；
4. 使用者当前的看法、疑问、矛盾或尚未想清楚之处。

如果这些信息已在主题素材地图或使用者补充中出现，不重复提问。缺少关键信息时使用 Grill Me 或普通逐问补足；未确认主线时不要急着生成一篇看似完整的文章。

## 整理文章

- 使用第一人称，保留使用者自己的用词、节奏、犹豫和未完成感；
- 优先从具体场景、真实动作或一个仍在发生的问题进入，不用空泛背景开头；
- 围绕一条主线组织材料，不写成输入摘要、周报或按日期排列的流水账；
- 外部输入负责提供触动和参照，生活经历负责提供文章的真实颗粒；
- 清楚区分外部来源的观点、使用者的判断和 AI 的推测；
- 不补写经历、人物、反馈、动机、情绪或引用；
- 不为了完整强行加入结论、行动建议或积极升华；
- 没有指定平台时，先写一篇平台中立的简单文章；材料少时宁可更短，不凑字数；
- 指定平台后再调整标题、长度、分段和开头，但不自动改成爆款腔或营销文案。

## 保存并持续打磨

首稿默认保存到 `practices/<输出练习名>/drafts/YYYYMMDD-文章主题.md`。日期使用首次创建草稿当天的日期；文件名中的主题应简短、具体、可辨认。创建前检查 `drafts/` 中是否已有同一主题草稿，有则更新原文件并保留原文件名。同一篇文章不自动创建 `v2`、`final` 或新的日期副本。

首次保存时包含工作标题、草稿正文、仍需确认的 0–3 处内容，以及实际使用过的 Review / Daily 路径；没有待确认项或来源时省略相应部分。后续收到“继续打磨”“改一下开头”等请求时，先读取同一草稿，只修改用户要求的部分，并保留尚未解决的问题。根据实际进度简要更新 Practice 的 `current.md`，但不要每次重写 `mission.md`。除非使用者明确要求且目标无歧义，否则不向任何平台发布。

## 飞书 Drive 执行与存储（重要）

豆包 / AI 环境中的本地文件通常是临时的。写入本地文件后必须上传到飞书 Drive 才算持久化；绝不能只创建本地 Markdown 就回复“已保存”。

使用相关 Daily 或 Review 前，先确认当前环境存在真实可调用的飞书云盘工具。没有工具时不要假装已经读取，可以请使用者直接提供材料。只读取与选定主题直接相关的文件，不为了丰富文章扫描全部云盘。

### 1. 定位或初始化输出 Practice

先搜索目标系统中的 `practices` 根目录：

```bash
lark-cli drive +search --query "practices" --doc-types folder --format json
```

- 找到 0 个 `practices`：只有在记录系统根目录已经明确时，才在该根目录下创建；无法确定父目录时让使用者选择，不要把它建在任意位置；
- 搜索到多个同名 `practices` 时，根据父目录、既有配置或已知 file token 消歧；无法确定时让使用者选择，不再创建一个根目录；
- 找到目标 `practices` 后，列出全部子项。若响应还有下一页，继续分页直到列完：

```bash
lark-cli drive files list --params '{"folder_token":"{practices文件夹token}","page_size":200}' --format json
```

使用者没有提供输出练习名时，先把 `{输出练习名}` 设为 `weekly-writing`。在 `data.files` 中精确筛选 `type == "folder"` 且 `name == "{输出练习名}"`：

- 找到 1 个 → 复用其 token；
- 找到 0 个 → 按“默认 Practice 的最小结构”准备 `mission.md` 与 `current.md`，创建 Practice 目录并上传两个文件；不要只创建空目录；
- 找到多个 → 停止创建，根据 `mission.md`、`current.md` 或既有 token 消歧；仍无法判断时让使用者选择。

只有精确匹配数量为 0 时，才执行初始化。`--file` 使用相对路径：

```bash
lark-cli drive +create-folder --name "{输出练习名}" --folder-token "{practices文件夹token}"
lark-cli drive +upload --file ./mission.md --folder-token "{输出练习文件夹token}"
lark-cli drive +upload --file ./current.md --folder-token "{输出练习文件夹token}"
```

保存三个接口返回的目录 token、文件 token 和链接。任一步失败都不继续创建 `drafts`，并明确说明默认 Practice 尚未完成初始化。

### 2. 定位或创建唯一的 `drafts`

列出输出 Practice 的全部子项：

```bash
lark-cli drive files list --params '{"folder_token":"{输出练习文件夹token}","page_size":200}' --format json
```

完整处理分页后，精确筛选 `type == "folder"` 且 `name == "drafts"`：

- 找到 1 个 → 复用其 token；
- 找到 0 个 → 只有此时才创建：

  ```bash
  lark-cli drive +create-folder --name "drafts" --folder-token "{输出练习文件夹token}"
  ```

- 找到多个 → 不再创建；优先使用已有 Practice 文件明确关联的 token，否则让使用者选择。

飞书允许同名文件夹并存。每一层都必须先查后建，不能因为第一次搜索没有命中就直接执行 `create-folder`。

### 3. 新建或更新草稿

先列出 `drafts` 的全部子项并处理完整分页，检查是否已有同一主题草稿：

```bash
lark-cli drive files list --params '{"folder_token":"{drafts文件夹token}","page_size":200}' --format json
```

- 找到 1 个同主题草稿 → 使用原文件名和 `file_token` 更新；
- 找到 0 个 → 使用首次起草日期创建 `YYYYMMDD-文章主题.md`；
- 找到多个 → 不再创建新文件，先让使用者确认需要继续哪一个。

新建时：

1. 在本地工作目录准备相对路径文件 `./YYYYMMDD-文章主题.md`；
2. 上传到唯一的 `drafts` 文件夹；
3. 保存返回的 `file_token` 和 URL。

```bash
lark-cli drive +upload --file ./YYYYMMDD-文章主题.md --folder-token "{drafts文件夹token}"
```

更新时：

1. 使用原 `file_token` 下载现有草稿到相对路径；
2. 在本地修改完整文件；
3. 使用同一个 `file_token` 覆盖上传，保留原文件名和链接。

```bash
lark-cli drive +download --file-token "{已有草稿的file_token}" --output ./YYYYMMDD-文章主题.md
lark-cli drive +upload --file ./YYYYMMDD-文章主题.md --file-token "{已有草稿的file_token}"
```

`--file` 和 `--output` 必须使用相对路径，不能使用绝对路径，否则可能触发 `unsafe file path`。

### 4. 更新 Practice 当前进度

只有本轮确实改变了输出练习的当前进度时，才更新同一 Practice 中已有的 `current.md`：先下载原文件，只修改必要段落，再用原 `file_token` 覆盖上传。不要新建第二个 `current.md`，也不要因为一篇文章改写长期 `mission.md`。

### 5. 成功与失败反馈

- 只有上传接口返回 `file_token`、URL 或等价成功结果后，才可以说草稿已经保存；
- 成功后返回飞书中的 Practice 名、草稿文件名、文件链接，以及本轮是新建还是更新；
- 上传失败时明确说明尚未持久化，返回建议路径和完整 Markdown；不要创建重复副本、改投其他目录或把临时本地路径当作交付结果。

## 完成检查

- 主题是否由使用者选择，而不是 AI 从 Review 中擅自决定？
- 是否写出了使用者真实做过或经历过的事情？
- 是否说明了主题为什么与使用者有关？
- 是否包含至少一个具体而可核对的细节？
- 是否保留必要的矛盾、不确定和未完成之处？
- 是否没有把外部来源的表达写成使用者自己的观点？
- 是否没有编造经历、情绪、反馈、引用或结论？
- 是否检查了第三方隐私和公开边界？
- 是否先给了使用者自由补充素材的机会，或按其要求跳过？
- 是否跨时间检索但只完整读取了高相关材料，没有全量扫描私人记录？
- 是否返回了带来源路径或链接的主题素材地图，并让使用者补充或校正？
- 是否在起草前确认了主线，或按使用者要求跳过 Grill Me？
- 草稿是否归入了真正的输出练习，而不是用文章主题临时冒充 Practice 名称？
- 使用者未提供输出练习名时，是否直接使用并复用了 `weekly-writing`，而不是中断流程追问名称？
- 是否创建或更新了同一篇草稿，而不是制造重复版本？
- 是否已把草稿上传到飞书 Drive，而不是只保存在临时本地文件？
- 是否复用了原 file token，避免重复文件和链接变化？
- 是否只保存和发布了使用者真正要求的结果？
